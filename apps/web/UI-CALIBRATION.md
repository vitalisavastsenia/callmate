# UI scope calibration

Baseline: foundation `0765159`, shared contract version 1. Scope reference: [delivery plan §4](../../docs/mvp-delivery-plan.md#4-engineer-1-ui-and-user-workflow) and [requirements](../../docs/requirements.md).

The original four-screen demo was a useful scaffold, but it did not satisfy the UI workstream: its request/summary were unstructured, its protocol was provisional, and it had no Stop, approval expiry, uncertainty state, history, calendar, readiness/settings, or browser tests. Its medical/vet example also differed from the documented non-sensitive barbershop scope.

## Validation and limits

Verified locally: workspace type checking, 21 shared-contract tests, 42 web unit tests, production build, and all 58 Playwright cases passed on desktop, narrow screens, and the HTTP/SSE client. This includes Settings defaults and draft-only edits, transport switching and active-call guards, inline/global approvals, offscreen recovery, and mocked background notifications. The browser suite covers history status mapping, the five-call filter threshold, combined search/filter behavior, the empty state, per-card Repeat, live attention and expiry, Home destination validation, required-field gating, bidirectional draft synchronization, normalized destination payloads, contact-save visibility, Home parsing/fallback, the manual Request, local contact selection/save/update/edit/delete, CSV/vCard mapping and deduplication, tone/notes in plans, timezone overrides and minute conversion, HTTP/SSE reconnect, lost Start responses, server-normalized plans requiring renewed review, remembered shareable details, approvals, and navigation during an active call. Desktop/narrow Home, request, plan, and Summary captures were inspected. Git whitespace checks passed. Run the commands in [README.md](README.md#verification). Automated coverage targets the UI workflow and wire boundary; it is not proof of real telephony performance, booking policy, provider cancellation, or privacy guarantees. Contacts and simulator settings/history use browser local storage, not production persistence. Expired conversation text is purged when saved simulator attempts are accessed.

No backend, Twilio/OpenAI SDK, database, provider callback, or dialogue-policy implementation was introduced. A later generic-request UI extension updates the central shared request/outcome schemas; backend consumers must adopt it before live integration. The UI renders server outcomes rather than inferring success from text or telephone termination. The browser cannot make authorization authoritative; the server must enforce the same reviewed references atomically before speech.

The next handoff is to connect the same screens and client to Engineer 2's private HTTP/SSE API, run the simulator scenarios together, then validate real calls jointly with Engineers 2 and 3. The real-call PoC, the required broader dialogue regression set (at least 20 Spanish scenarios), and the integrated personal MVP are not declared complete by this UI work.

## Generic request UI extension

Requests now start empty and support appointments, questions, change/cancel, and other goals, with explicit templates, editable boundaries, shared privacy fields, and collapsed EUR call limits. Review/live/result/history retain the generic request. Non-booking results distinguish answered findings from required follow-up and never fabricate a booking or calendar entry. Existing booking scenarios remain covered; custom simulator tasks do not mutate existing appointments. See [the extension contract](../../docs/ui-message-contract.md#generic-request-extension).

In simulator mode, Home's “Prepare the plan” suggests type-specific fields and boundaries from the English goal. Request also offers “Fill details from goal”; automatic parsing is optional for manual review. Suggestions are highlighted and editable, preserve manual values, and require review. Relative dates resolve in the destination timezone. A parse failure or missing required detail opens Request with “Couldn't understand everything — fill in the details” and preserves recognized values. The single `parseGoal()` client entry point can later connect to a validated backend endpoint; backend mode currently falls back to manual entry.

Home contains the natural-language goal, optional templates, and a compact shared contacts/destination block. Goal, name, and valid phone are required before preparation, with inline phone validation and a missing-fields hint; formatted numbers normalize to E.164. New contacts save only when opted in, and Home hides the save checkbox for existing numbers. The hero’s Request tab link and navigation preserve the shared goal/destination draft in both directions. Parsing preserves manually supplied destination details. Request is the full manual form, ordered as Who to call, request type/goal/type-specific fields, tone/notes, boundaries, sharing, and collapsed Advanced settings. The phone country selector defaults to +34. Advanced summarizes timezone, duration in minutes, and maximum estimated EUR cost; serialization retains seconds and the existing limits. “Review call plan” validates the draft and shows the compact “Zeus will…” card. Edits invalidate review; Call requires a valid reviewed snapshot and readiness. The live call replaces the plan, then a short result links to Summary. New sections scroll into view and respect reduced-motion preferences.

Navigation is Home, Request, Summary, and Settings; contacts stay inside the shared Name combobox. Active tabs are filled gold. Summary displays newest-first cards with business, date, request type, an outcome badge, one-line summary, details, and Repeat. Above five calls, search and status filters combine and offer a clear action for no matches. Per-card Repeat fetches the saved full request and prefills Request without dialing; uncertainty warnings remain explicit. The empty state has the mascot and a Create a request action. Needs your attention appears only for an unexpired pending approval and updates live while on Summary; Answer Zeus returns to the exact offer. Calls-to-dial-later are not represented in the current API or simulator, and future booked appointments are not treated as scheduled calls. Drafts and active calls survive navigation. Destination contacts live behind the isolated localStorage contacts service, including normalized-phone deduplication and explicit saves through the edit dialog. Selecting a contact copies its name, phone, timezone, tone, and notes into the draft. Settings owns remembered defaults for the shareable name, callback number, email, and timezone. Request-only edits do not change those defaults or fill the business destination. Duration/cost/retention still use the existing settings API. Mode selection is remembered locally and locked during active, pending, or unresolved attempts. Mode changes reload the selected transport history/readiness without losing the editable draft.

New plan requests carry `tone`, `tone_notes`, and optional `contact_id` through the central shared schemas, HTTP client, simulator, and review details. They remain optional for reading older plans; tone/notes do not grant authority or sharing permission. Backend consumers must adopt these fields before integration.

The Home hero shows “No drama. Zeus will llama.” in the small gold uppercase eyebrow style above “Leave the call to Zeus.” Its description is “Tell Zeus what you need in your own words below — or fill in the details yourself on the Request tab. Zeus calls in the language you need and checks with you before any decision that needs your approval.” “Request tab” links to the manual form without resetting the draft. The larger mascot blends into the page background. Navigation sits at the upper right of the header; the Simulator/Live badge and How it works section are removed. The existing header branding remains. The compact Request uses pill types, inline errors, editable boundary tags, sharing fields in a row and a sticky readiness bar. Summary uses the resting mascot and opens Home from its empty-state action. Inline approvals also appear as a direct-answer bottom panel when out of view or on another page; background alerts use optional notification/sound and title flashing. Approvals retain the agreed exact-offer approve/reject contract; no free-text or callback endpoint is added. These visual changes do not extend the simulator's existing Spanish/English language support or change call mode/readiness behavior.
