# Shared interfaces v1

Status: implementation baseline for review by the three engineers; no human sign-off is implied. Updated: 2026-10-15. This is the technical reference for the [three-engineer integration agreement](engineering-contract.md), expanding [delivery-plan section 3](mvp-delivery-plan.md#3-agree-interfaces-before-parallel-implementation).

Use the [backend to UI message contract](ui-message-contract.md) for scenario-specific messages, expected UI behavior, and concrete JSON examples. It documents use of these interfaces without implementing the application.

## 1. Deliverables and ownership

The executable source of truth is [`@callmate/contracts`](../packages/contracts/src/index.ts). It exports Zod runtime schemas, inferred TypeScript types, private HTTP route definitions, and internal adapter interfaces. [`@callmate/contracts/fixtures`](../packages/contracts/src/fixtures.ts) provides synthetic example data. It is a separate export so production consumers do not import examples by default.

| Boundary | Producer | Consumer | Owner |
| --- | --- | --- | --- |
| HTTP requests/responses and SSE | Local API / browser | Browser / local API | Engineer 2 maintains schemas; Engineer 1 reviews. |
| Dialogue inputs and candidate actions | Controller / dialogue engine | Dialogue engine / controller | Engineer 3 maintains dialogue implementation; Engineer 2 reviews contract changes. |
| Policy decisions and playback permits | Policy / controller | Controller / voice adapter | Engineers 2 and 3 jointly review changes. |
| Telephony and normalized voice events | Twilio/voice adapters | Controller | Engineer 2. |
| Example data and UI scenarios | Shared fixture package | All three engineers | Engineer 2 maintains common data; each engineer contributes failure cases. |

No backend, dialer, simulator engine, UI, or model integration is implemented by these contracts. The schemas can be consumed immediately by those implementations.

The [Docker backend](docker-development.md) implements these private HTTP/SSE routes for persisted simulator attempts. Fake telephony/dialogue/text-voice adapters consume the shared ports; live adapters remain future work. `SimulatorScenarioSchema` exports configuration scenario IDs without adding fields to the existing HTTP/event formats.

## 2. Common conventions

- All JSON object schemas reject unknown properties. Parse external data at boundaries; TypeScript annotations alone do not validate JSON or model output.
- IDs are UUID strings generated by the backend. Plan/offer versions start at 1 and are immutable: a change produces a new version. Attempt IDs never double as provider call IDs.
- Instants include an explicit UTC offset. Availability/appointment values include `localDate`, `localTime`, IANA `timeZone`, and the corresponding `instant`, at minute precision. Schemas reject inconsistent combinations and nonexistent local times. For a repeated DST hour, the UI/backend must explicitly resolve and review the intended occurrence; never choose one silently.
- Service prices use integer EUR cents. Call costs use integer USD cents in v1. Unknown prices and unavailable costs are `null`, never zero. Currency conversion is outside scope.
- English is the UI/translation language; business conversation text is tagged `es-ES`. Other languages need a contract change.
- E.164 validation checks number syntax, not reachability or dialing permission. The backend separately enforces approved destination, Spain/country restrictions, permitted caller ID, blocked/special destinations, and spending limits.
- Live and simulator mode are explicit on call requests, snapshots, and history. The simulator cannot dial, and an existing attempt's mode cannot change.
- Settings contain no credentials. Provider keys and provider-specific configuration remain local to the backend.

## 3. Core schemas

| Schema | Meaning / invariant |
| --- | --- |
| `RequestDraftSchema` | Business, service, booking name, explicit availability, price policy, booking authority, allowed contact details, and separate call limits. All availability windows use one business timezone. |
| `ReviewPlanSchema` | Backend-issued immutable plan ID/version, creation time, and normalized request. Ready for user review but not yet authorized to dial. |
| `ApprovedPlanSchema` | The reviewed plan plus backend-recorded approval time. Created atomically when the user starts an attempt. |
| `OfferSchema` | Complete proposed slot/service/name, nullable price/duration, deposit/fee/add-on conditions, offer version, and message evidence IDs. Unknown conditions are representable but are not permission to accept. |
| `ApprovalRequestSchema` | One offer, attempt and approved-plan binding, primary reason, creation time, and backend-owned expiry. |
| `ApprovalDecisionSchema` | Approve/reject with approval ID and exact plan/offer versions. The browser cannot replace an offer, set its expiry, or send arbitrary new booking constraints. |
| `CallSnapshotSchema` | Authoritative current view: mode, approved plan, telephone state, separate booking state/outcome, active offer, pending approval, messages, usage, revision, and event cursor. |
| `TranscriptMessageSchema` | Stable message/turn IDs, speaker, Spanish text, optional English translation, final/provisional marker, and playback state. Generated speech is not automatically marked played. |
| `OutcomeSchema` | `pending`, `confirmed`, `not_booked`, or `uncertain`. A confirmed outcome carries exact offer details and finalized business-message evidence. |
| `UsageSchema` | Estimates and available settled total are separate. Mark settled only after all enabled billable components have been accounted for. |

Schemas validate structure and some cross-field consistency, not the truth of a conversation or all booking policy. Before confirming a booking, the backend must check that the cited final business statements actually confirm the specific offer, after permitted acceptance. A syntactically valid action or evidence ID is insufficient.

While conversation data is retained, confirmed snapshots require evidence IDs to point to finalized business messages in that snapshot. After retention/deletion, `conversationData: "deleted"` requires an empty transcript and a terminal call; preserve the structured booking and opaque evidence references, not the deleted text. Delete transcript-bearing event payloads too. Evidence validity must be established before deletion, not reconstructed afterward.

## 4. Private HTTP API

All routes below use the loopback UI/API listener. They are never mounted on the public Twilio callback listener. Canonical methods, paths, body/query schemas, and response schemas are exported as `api` in [`http.ts`](../packages/contracts/src/http.ts).

| Method and path | Request | Success |
| --- | --- | --- |
| `GET /api/v1/readiness` | None | `200 ReadinessSchema`; current configured mode/engine and non-secret checks. |
| `POST /api/v1/plans` | `RequestDraftSchema` | `201 { plan: ReviewPlan }`; backend normalization must be shown before Start. |
| `POST /api/v1/calls` | `StartCallRequestSchema`; `Idempotency-Key` header | `202 { call: CallSnapshot }`; asynchronous creation, not a promise of connection. |
| `GET /api/v1/calls/:attemptId` | UUID path parameter | `200 { call: CallSnapshot }`. |
| `POST /api/v1/calls/:attemptId/stop` | Empty JSON object | `202 { call: CallSnapshot }`; repeatable, including for an already ended call. Acknowledged hangup is reflected separately in state. |
| `POST /api/v1/calls/:attemptId/approvals` | `ApprovalDecisionSchema`; `Idempotency-Key` header | `200 { call: CallSnapshot }`; recorded decision, not proof that acceptance was spoken. |
| `GET /api/v1/calls/:attemptId/events` | Optional `Last-Event-ID` | `200 text/event-stream`. |
| `GET /api/v1/history` | `limit` 1–100, default 20; optional UUID cursor | `200 { items: HistoryEntry[], nextCursor: string | null }`. |
| `DELETE /api/v1/calls/:attemptId/conversation` | None | `200 { attemptId, deleted: true }`; removes local transcript/translation/event text, preserving booking metadata. |
| `GET /api/v1/settings` | None | `200 SettingsSchema`. |
| `PUT /api/v1/settings` | `SettingsSchema` | `200 SettingsSchema`; affects future plans, never mutates an active approved plan. |

### Required server behavior

- Start atomically validates plan/version, current readiness and mode, and the single-call reservation, then persists the approved plan and attempt before contacting Twilio. Check availability is still in the future and budgets remain permitted. User review of a plan is not itself permission to dial.
- An `Idempotency-Key` is a UUID. Reusing it with the same command returns the same attempt/recorded decision and current snapshot; a different body or endpoint returns `409 IDEMPOTENCY_CONFLICT`. Persist keys/outcomes so a process restart cannot make a retry dial again. Keep start-key tombstones for the life of an attempt, including after conversation deletion.
- If provider creation times out, persist `reconciliation_required` and do not redial automatically. That state holds the active-call reservation until reconciled.
- Approval checks are atomic: active call, current pending approval, identical attempt/plan/offer versions, and `now < expiresAt`, using the backend clock. A changed offer invalidates the pending approval. Only already-permitted service/time/price exceptions may be approved; deposits, payments, add-ons, and cancellation fees remain excluded.
- Valid approval is a grant for that specific offer. A rejected, expired, invalidated, or already-consumed conflicting decision is never treated as acceptance. Check authority again immediately before playback. Do not expire an appointment merely because the user-approval deadline later passes after authorized speech.
- Conversation deletion is allowed only for a terminal call; repeated deletion succeeds. Purge text from local event replay storage as well as messages, and invalidate any replay range affected by deletion.
- History order is descending `(createdAt, id)`. The cursor is the last returned attempt ID; backend resolves its ordering tuple. Unknown cursors return `400 INVALID_REQUEST`. Empty history returns `items: []`, `nextCursor: null`.
- Keep local mutating routes protected against cross-origin requests/CSRF even when bound to loopback. Missing signature or unrecognized provider session on the separate callback listener is rejected before it can touch these interfaces.

### Errors

Use `ApiErrorSchema`: `{ error: { code, message, requestId, details: [{ path, message }] } }`. Messages describe the problem without keys, raw request values, or transcript bodies. Do not return internal stack traces.

| HTTP status | Codes |
| --- | --- |
| 400 | `INVALID_REQUEST`, `EVENT_CURSOR_INVALID` |
| 404 | `NOT_FOUND` |
| 409 | `PLAN_VERSION_MISMATCH`, `CALL_ALREADY_ACTIVE`, `IDEMPOTENCY_CONFLICT`, `APPROVAL_STALE`, `APPROVAL_EXPIRED`, `CALL_NOT_ACTIVE`, `MODE_MISMATCH`, `DATA_NOT_DELETABLE` |
| 503 | `PROVIDER_NOT_READY`, `PROVIDER_UNAVAILABLE` |
| 500 | `INTERNAL_ERROR` |

`POST /calls` returning 503 before any provider request may be retried by the user. After an ambiguous provider request, return/retrieve the existing attempt and reconcile; a generic error must not encourage a new dial.

## 5. Events and reconnects

`DomainEventSchema` uses `{ contractVersion: 1, id, attemptId, sequence, snapshotRevision, occurredAt, type, payload }`. Sequence starts at 1 per attempt, increases monotonically, and is persisted with the snapshot update in one transaction. Multiple events can belong to one snapshot revision. The backend serializes all updates to an attempt.

Event types: `call.status`, `transcript.updated`, `offer.updated`, `approval.requested`, `approval.resolved`, `booking.updated`, `usage.updated`, `conversation.deleted`, and `call.error`. Consumers use the exported discriminated union; no raw Twilio/OpenAI events cross into the UI.

```text
id: 1
event: callmate
data: {"contractVersion":1,"id":"...","attemptId":"...","sequence":1,"snapshotRevision":2,"occurredAt":"...","type":"call.status","payload":{"callState":"ringing"}}

```

The abbreviated envelope above illustrates framing, not valid UUID/timestamp data. Import validated fixtures for executable examples.

Reconnect protocol:

1. Fetch a snapshot; render its messages/state and retain `lastEventSequence`.
2. Open the attempt's SSE endpoint with `Last-Event-ID` set to that cursor, including `0` for an attempt with no events. Browser clients needing an initial custom header can use fetch streaming; native EventSource requires a separate initial-cursor mechanism, so do not assume it supports custom headers.
3. Replay events after the cursor, then tail live updates without a replay/live race. Deduplicate by sequence/message ID. Update a provisional message or translation in place rather than appending duplicates.
4. If a cursor is beyond the latest event or its replay range was removed, emit unnumbered `event: reset` with `{ "reason": "snapshot_required" }` and close. Refetch the snapshot and reconnect from its new cursor. Malformed cursor strings return the normal 400 error before opening the stream.
5. Heartbeats are SSE comments and have no event ID. They do not change sequence or snapshot revision. On a sequence gap, unsupported contract version, or unknown event, the client resynchronizes instead of guessing state.

The deletion event tells an attached client to clear cached transcript text. A snapshot after deletion contains no messages; older clients with replay gaps must reset. This protects local UI consistency and does not promise deletion from external providers.

## 6. Controller, dialogue, and voice boundaries

[`ports.ts`](../packages/contracts/src/ports.ts) defines internal interfaces. Engineer 2 implements the controller/provider side; Engineer 3 implements dialogue/policy functions. Runtime model output uses `DialogueProposalSchema` and `CandidateActionSchema`, not unchecked type casts.

| Interface | Contract |
| --- | --- |
| `TelephonyPort` | Start a call, request hangup, query call state. Creation/hangup may return unknown status. Provider IDs stay internal. |
| `DialoguePort` | Final business speech and approved context in; typed candidate action and translations out. AbortSignal cancels obsolete work. Trigger must reference a final business message. |
| `BookingPolicyPort` | Current snapshot, candidate, server time, and server-resolved grant in; allow with controlled Spanish text, ask-user, clarify, or deny out. No database or provider side effects. |
| `TextVoicePort` | ConversationRelay adapter sends only authorized text and supports cancelling obsolete output. |
| `NativeAudioVoicePort` | Realtime candidate adapter releases only buffered, authorized output for the specified permit. Audio bytes and provider event formats stay inside the adapter. |

The controller matches dialogue results to the current attempt/turn/version and rejects late results. It verifies grants, persists the decision, and mints a `PlaybackPermit` tied to plan, offer, turn, output, exact approved Spanish text, and expiry. The voice adapter verifies the permit against controller-owned state; merely parsing a permit-shaped object does not authorize playback. Neither the browser nor model can issue one.

Permits are single-use and invalidated by interruption, changed offers, Stop, expiry, or stale turns. Interrupted audio is discarded rather than released on a late approval. Maintain real playback state independently of generated text.

Realtime is an experimental adapter boundary, not an implemented or automatically selected provider. Native output starts withheld; the bridge must associate text with audio and check it before release. Tool approval alone cannot prevent an unauthorized spoken commitment. If that check is unavailable, cannot match the approved content, or adds unacceptable latency, readiness fails for live native-audio mode and the implementation must retain controlled text playback. The contracts do not assert that this mechanism has already been proven.

Current architecture/stack documents retain ConversationRelay as the documented baseline pending the Realtime spike. UI, plans, approvals, events, and booking outcome contracts are the same for either implementation.

## 7. Usage and validation

At repository root, run checks in Docker (no host Node.js required):

```sh
docker compose --profile checks run --build --rm checks
```

The container runs root type checking and tests for contracts and the backend/simulator with external networking disabled. It does not dial or contact model/voice providers. Container builds generate package JS/declarations; host build output and dependencies are ignored by Git and excluded from the Docker context.

```ts
import { api, CallSnapshotSchema, type CallSnapshot } from "@callmate/contracts";
import { connectedCallFixture } from "@callmate/contracts/fixtures";

const snapshot: CallSnapshot = CallSnapshotSchema.parse(connectedCallFixture);
const route = api.startCall; // method, path, request schema, response schema
```

The tests cover malformed input, unknown properties, currencies, DST resolution, plan/offer binding, terminal outcomes, evidence references, deletion, event versions/cursors, and model/playback shapes. Server implementations must add behavioral tests for transactions, idempotency/restart, policy, deadlines, replay ordering, CSRF/signatures, and actual audio cancellation. Schema tests do not replace these checks.

## 8. Change process

Engineer 2 maintains shared definitions; Engineers 1 and 3 review affected boundaries before merging. Contract v1 is an app protocol version, separate from the package's development version. Renames, removed fields, stricter semantics, or new event variants require coordinated consumer updates and a version bump. Update fixtures, tests, and this document together. Do not duplicate schema definitions in the frontend or backend.

## 9. Persisted manual mock calls (development extension)

The existing booking `CallSnapshotSchema` and plan/start contracts remain unchanged. `GET /api/v1/calls/:attemptId` and Stop now return `StoredCallSnapshotSchema`, the union of a booking snapshot and `ManualCallSnapshotSchema`. Manual attempts originate from the local console's strict `POST /api/dev/conversations` input:

```json
{
  "requestId": "10000000-0000-4000-8000-000000000010",
  "initialMessage": "Hola, quisiera información.",
  "language": "es-ES"
}
```

`requestId` is also the persisted attempt ID and the globally namespaced idempotency key. Reusing it with different input or for another endpoint returns `409 IDEMPOTENCY_CONFLICT`. Manual calls share the database-enforced active slot with scripted calls. The console response remains `{ "conversation": ... }` as documented in the Docker guide; it is a projection of the same attempt.

| Snapshot field | Manual meaning |
| --- | --- |
| `kind` | Always `"manual_mock"`; history entries also include this marker. |
| `mode` / `plan` | `"simulator"` / `null`; no invented review plan or booking authority. |
| `language` | `es-ES`, `ru-RU`, `en-US` or `pl-PL`. |
| `callState` | Shared lifecycle enum; disconnected/ambiguous calls use `reconciliation_required` and retain the active slot. |
| `bookingState` / `outcome` | `pending` while active; `not_booked` after termination. A normal manual end has reason `development_only`. No offer, approval or confirmed booking is permitted. |
| `activeOffer` / `pendingApproval` | Always `null`; approval commands return `409 CALL_NOT_ACTIVE`. |
| `messages` | `ManualTranscriptMessageSchema[]`: exact text up to 8,000 characters, locale tag, final-only, and `translationEn: null`. |
| Assistant `playback` | `withheld` before relay setup; `generated` after submission. Neither is proof of audible playback. Business messages use `not_applicable`. |
| Other fields | Shared revisions/sequences/timestamps, conversation deletion state, and unavailable usage. |

SSE uses the existing envelope and event names. `transcript.updated` accepts the manual transcript schema as well as the existing Spanish booking schema; fetch the snapshot first to identify its kind. An initial assistant message has one stable message ID: the withheld and generated events update that same message rather than append two messages. Final business utterances append messages; partial fragments are not published. No translation, offer extraction, approval or confirmation is fabricated.

The common GET/Stop/history/deletion/SSE routes work for either kind. Deletion removes manual text from snapshots, compatibility views and replay payloads; request digests retain idempotency without keeping the deleted input. A stale SSE cursor receives the existing `reset` event. Direct operator-created echo calls without a backend attempt remain outside this API.

Manual mock calls persist provider identity, CallSid/session IDs, a relay-token hash and creation intent. Startup and relay-loss recovery reconcile known calls and hang up active orphans without redial or replaying text; uncertain calls retain the shared reservation. A valid signed mock callback or late setup may recover an unknown SID for reconciliation/hangup. See the [recovery rules and unresolved cases](docker-development.md#10-persistent-correlation-and-recovery). The development projection adds nullable `sessionId`; shared v1 snapshot/SSE formats remain unchanged.

Signed mock status callbacks now use a durable per-attempt sequence, forward-only provider progress and an immutable terminal state; callbacks and delayed REST results cannot reopen calls, clear Stop/recovery, or restore deleted messages. Cursor-only updates do not change UI revisions or SSE sequences. See the [event handling rules](docker-development.md#11-reliable-mock-status-callbacks).

This extension does not enable live mode, real Twilio routes, WS signature verification, dialogue integration or provider billing. Keep the callback listener local.

Manual mock call controls enforce persisted per-attempt duration and caller-inactivity deadlines without changing shared v1 payloads. Explicit Stop is idempotent and reports `user_stopped`; deadline-triggered termination reports `technical_failure` with a duration/silence summary. Unconfirmed termination keeps the shared active slot and blocks output. See [call controls](docker-development.md#12-call-controls-and-limits) for configuration, dialing races and restart rules.
